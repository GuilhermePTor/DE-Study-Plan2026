Part I — Core Concepts
01

Incremental Models

Only process what changed — not everything that exists

The simplest possible explanation

Imagine you work at a library with one million books. Every week, 500 new books arrive. Your job is to keep the library's catalogue up to date.

You have two options. Option A: every week, take every single book off every shelf, scan it, and put it back. One million scans per week. Option B: only scan the 500 new arrivals. Five hundred scans per week.

Option B is what an incremental model does. It only processes the rows that are new or changed since the last run. Option A is a full refresh — correct and simple, but wasteful at scale.

📬 Analogy — The Email Inbox

You have 12,000 emails. You read them all last Friday. Today is Monday. Three new emails arrived over the weekend.

Do you re-read all 12,000 to "catch up"? No — you read the 3 new ones. The timestamp of the last email you read on Friday is your watermark. Everything after that watermark is new. That's incremental loading.

The three components every incremental model needs

ComponentWhat it doesConcrete example
Watermark The "last seen" boundary. Rows after this timestamp get picked up on the next run. MAX(updated_at) stored from the previous successful run
Filter Applies the watermark to the source query — only fetches the delta. WHERE updated_at > '2024-07-14 23:59:59'
Write strategy How new and changed rows land in the target table. MERGE (upsert), INSERT, or partition overwrite

The watermark in depth

The watermark is the most important concept in incremental loading. Think of it as a bookmark in a book. When you stop reading, you leave a bookmark. Next time you open the book, you start from the bookmark — not from page 1.

In SQL, the watermark is typically the maximum value of a timestamp column — usually updated_at or event_date — from the last successful run. It gets saved somewhere: a metadata table, an Airflow variable, a dbt state file. The next run reads it, uses it as a filter, and after finishing successfully, updates it to the new maximum.

⚠️ The watermark trap

The watermark must only be updated after the load succeeds. If you update it first and then the load crashes, the next run will skip the rows that were never actually loaded — and you'll have a silent data gap. Always: load first, update watermark second.

The SQL pattern

incremental_load.sql
-- Step 1: find the watermark from the last successful run
SELECT MAX(updated_at) AS last_watermark
FROM   target_events;
-- returns: '2024-07-14 23:59:59'

-- Step 2: load only new/changed rows
INSERT INTO target_events
SELECT event_id, user_id, event_type, event_date, updated_at
FROM   source_events
WHERE  updated_at > '2024-07-14 23:59:59';

-- Step 3 (ONLY after Step 2 succeeds): update the stored watermark
UPDATE pipeline_metadata
SET    last_watermark = NOW()
WHERE  pipeline_name  = 'target_events_load';

The dbt version

In dbt, incremental models are a first-class feature. dbt handles the watermark automatically using the is_incremental() macro and the model's own existing data:

models/stg_events.sql
-- Tell dbt: build this as an incremental table, deduplicate on event_id
{{ config(
    materialized='incremental',
    unique_key='event_id'
) }}

SELECT
    event_id,
    user_id,
    event_type,
    event_date,
    updated_at
FROM {{ source('raw', 'events') }}

-- This block only runs on the 2nd+ run (not the first full load)
{% if is_incremental() %}
  WHERE updated_at > (SELECT MAX(updated_at) FROM {{ this }})
{% endif %}
💡 What dbt does under the hood

On the first run, is_incremental() is false — dbt builds the entire table from scratch (like a full refresh). On every subsequent run, it's true — dbt runs the filtered query and merges the results into the existing table using the unique_key to decide: "does this row already exist? Update it. Does it not exist? Insert it."

When to use incremental — and when not to

✅ Good candidate for incremental

  • Table has tens of millions of rows or more
  • Source has a reliable updated_at or created_at timestamp
  • Only a small fraction of rows change per run
  • Load runs hourly or more frequently
  • Compute cost is billed per byte scanned (BigQuery, Snowflake)

❌ Stick with full refresh

  • Table is small (< 5 million rows)
  • Source has no reliable timestamp to filter on
  • Source deletes rows (incremental won't catch deletions)
  • You need guaranteed correctness and can afford the cost
  • The transformation logic is complex and hard to partition
✓ The one sentence to remember

An incremental model says: "I already have most of the data — just give me what changed since last time." The watermark is the bookmark. The MERGE is what keeps it safe to re-run.

02

SCD Type 1

When a value changes, overwrite it — and forget the past

What is a Slowly Changing Dimension?

Before explaining Type 1, let's understand the parent concept. In data warehousing, facts are the measurements you record — sales amounts, meter readings, clicks. Dimensions are the context around those facts — the customer who made the sale, the product that was sold, the device that was clicked.

Dimensions "change slowly" — they don't update with every transaction, but they do change over time. A customer moves cities. A product changes its price. An employee changes departments. How you handle those changes defines whether you're using Type 1, Type 2, or another strategy.

📱 Analogy — The Contacts App

You have Alice in your contacts. Her email was alice@oldcompany.com. She changed jobs. You open Contacts, tap Edit, type alice@newcompany.com, and save.

The old email is gone. Completely. Your contacts app doesn't remember it ever existed. If someone asked you "what was Alice's old email?" you'd have no idea. That's SCD Type 1 — overwrite and forget.

This is fine for a contacts app. Whether it's fine for a data warehouse depends entirely on whether you ever need to ask "what was Alice's email when X happened?"

The formal definition

SCD Type 1 is a dimension update strategy where changed attribute values are overwritten in place. No history of previous values is preserved. The table always reflects the current, latest state of each record.

What it looks like in the table

Before — Alice's record

customer_id | email         | city
1001        | alice@old.com | Porto

After Type 1 update

customer_id | email         | city
1001        | alice@new.com | Lisbon  ← old values gone

One row per customer. Always. The old values are irretrievable unless you have a backup or audit log elsewhere.

The SQL pattern

The standard Type 1 implementation uses a MERGE statement — update if the record already exists and something changed, insert if it's brand new:

scd_type1.sql
MERGE INTO dim_customers    AS target
USING      stg_customers    AS source
ON         target.customer_id = source.customer_id

-- Row exists AND at least one attribute changed → overwrite
WHEN MATCHED AND (
    target.email <> source.email OR
    target.city  <> source.city
)
THEN UPDATE SET
    target.email      = source.email,
    target.city       = source.city,
    target.updated_at = NOW()

-- Row doesn't exist yet → insert fresh
WHEN NOT MATCHED THEN INSERT (
    customer_id, email, city, created_at, updated_at
) VALUES (
    source.customer_id, source.email, source.city, NOW(), NOW()
);
💡 Why the change-guard matters

Notice the WHEN MATCHED AND (target.email <> source.email OR ...) condition. Without it, every single existing row gets an UPDATE statement on every run — even rows where nothing changed. That wastes I/O, inflates updated_at timestamps falsely, and can break incremental downstream models that use updated_at as a watermark. Only write what actually changed.

When Type 1 is the right choice — and when it destroys your data

✅ Type 1 is fine when...

  • You're correcting a data entry error (typo in a name, wrong postcode)
  • The attribute has no meaningful history (phone number, login email)
  • Downstream reports only ever need current state
  • You have an audit log at the source system level anyway

❌ Type 1 destroys history when...

  • You need to answer "what was X at the time of this transaction?"
  • Customer segmentation or pricing depended on the old value
  • Regulatory compliance requires a full change trail
  • The attribute drives business logic that affects historical fact rows
⚠️ The silent data destruction problem

Type 1 is dangerous precisely because nothing breaks when you use it in the wrong place. The query still runs. The dashboard still loads. But the numbers are quietly wrong — because you're now joining historical orders to Alice's current address instead of the address she had when the order was placed. The error is invisible until someone does a deep audit.

✓ The one sentence to remember

SCD Type 1 says: "I only care about what's true right now. The past is irrelevant." Use it when history genuinely doesn't matter. Avoid it when you might ever need to answer a question about the past.

03

SCD Type 2

Keep every version of a record — and travel back in time with a join

The problem that Type 2 solves

Let's stay with Alice. She's a customer. She lived in Porto in January, moved to Lisbon in March. She placed an order on January 15th.

In April, your finance team runs a report: "Show me all orders, and the city the customer lived in at the time of the order."

If you used Type 1 and overwrote her address to Lisbon, Alice's January order now shows Lisbon. That's wrong. The free shipping threshold, the tax rate, the delivery zone — all would be wrong. History is destroyed.

SCD Type 2 solves this by keeping every version of Alice's record, each stamped with the dates it was valid. Now you can always reconstruct what her city was on any given date.

📅 Analogy — The Passport

When you renew a passport, the issuing office doesn't delete your old one from their records. They mark it "expired" and issue a new one. Their database has both: passport #1 valid 2015–2020, passport #2 valid 2020–present.

If a border agent checks "was this person legally allowed to travel on July 3rd, 2018?" they can look at the history and find passport #1 — which was valid then. If the old record had been overwritten (Type 1), that question could not be answered. Type 2 is the passport database approach.

What the table looks like

dim_customers — Type 2 table
-- Before Alice moves:
sk | customer_id | email           | city   | valid_from | valid_to   | is_current
1  | 1001        | alice@new.com   | Porto  | 2022-01-01 | 9999-12-31 | TRUE

-- After Alice moves to Lisbon (March 15, 2024):
sk | customer_id | email           | city   | valid_from | valid_to   | is_current
1  | 1001        | alice@new.com   | Porto  | 2022-01-01 | 2024-03-14 | FALSE  ← closed
2  | 1001        | alice@new.com   | Lisbon | 2024-03-15 | 9999-12-31 | TRUE   ← new version

The four extra columns — and why each one exists

sk
Surrogate Key — the most important column

A unique integer (or UUID) assigned to each row, not each customer. This is what your fact table stores as a foreign key. It pins a fact record to the exact version of the dimension that was active when the fact occurred. Without it, you can't do point-in-time joins. More on this below.

↑
valid_from — when this version started

The date this version of the record became active. Usually the date the change was processed. For Alice's new row, it's March 15, 2024 — the day she moved.

↓
valid_to — when this version ended

The date this version was superseded. A far-future sentinel value — 9999-12-31 — means "still active." When a record changes, you set the old row's valid_to to yesterday, and insert a new row with valid_to = 9999-12-31.

✓
is_current — the shortcut flag

A boolean set to TRUE only on the most recent version. Purely a convenience column — it lets you write WHERE is_current = TRUE instead of WHERE valid_to = '9999-12-31'. Both do the same thing; is_current is just more readable and often faster with an index.

The surrogate key — the hardest concept to grasp

This is where most people get confused. Let's slow down.

Alice's natural key is customer_id = 1001. She now has two rows in dim_customers — both have customer_id = 1001. So if your orders table stores customer_id = 1001, which row do you join to?

You can't know. That's the problem.

The solution: the orders table doesn't store customer_id. It stores customer_sk — the surrogate key. When Alice placed her order in January, her surrogate key was 1 (the Porto version). That 1 gets stored on the order. Now when you join, you always land on the right version:

point_in_time_join.sql
-- fact_orders stores customer_sk, not customer_id
SELECT
    o.order_id,
    o.order_date,
    o.amount,
    c.city           AS city_at_time_of_order,  -- Porto ← correct!
    c.customer_id,
    c.email
FROM  fact_orders    o
JOIN  dim_customers  c
  ON  o.customer_sk = c.sk;
-- The surrogate key pins the join to the exact version.
-- No date-range logic needed at query time.
💡 Why 9999-12-31 and not NULL?

You might think: "just use NULL for open-ended records." The problem is that BETWEEN and range comparisons don't work cleanly with NULLs — order_date BETWEEN valid_from AND NULL returns nothing. Using a far-future sentinel like 9999-12-31 means you can always write WHERE order_date BETWEEN valid_from AND valid_to and get the right answer, because every real date is less than 9999-12-31.

The SQL pattern — "close and insert"

Applying a Type 2 change is a two-step operation: first close the old row, then insert the new one.

scd_type2.sql
-- ── STEP 1: Close rows that have changed ──────────────────────────────
UPDATE dim_customers
SET
    valid_to   = CURRENT_DATE - INTERVAL '1 DAY',
    is_current = FALSE
WHERE is_current = TRUE
  AND customer_id IN (SELECT customer_id FROM stg_customers)
  AND (
        email <> (SELECT email FROM stg_customers s
                  WHERE s.customer_id = dim_customers.customer_id)
     OR city  <> (SELECT city  FROM stg_customers s
                  WHERE s.customer_id = dim_customers.customer_id)
      );

-- ── STEP 2: Insert new versions (changed + brand-new records) ─────────
INSERT INTO dim_customers (
    customer_id, email, city,
    valid_from, valid_to, is_current
)
SELECT
    s.customer_id,
    s.email,
    s.city,
    CURRENT_DATE       AS valid_from,
    '9999-12-31'::date  AS valid_to,
    TRUE               AS is_current
FROM stg_customers s
WHERE NOT EXISTS (
    -- Skip if an identical current row already exists (no change)
    SELECT 1
    FROM   dim_customers d
    WHERE  d.customer_id = s.customer_id
      AND  d.is_current  = TRUE
      AND  d.email       = s.email
      AND  d.city        = s.city
);

Querying a Type 2 dimension

query_patterns.sql
-- Get the current state only (most common)
SELECT * FROM dim_customers WHERE is_current = TRUE;

-- Get the state at a specific date (point-in-time)
SELECT * FROM dim_customers
WHERE customer_id = 1001
  AND '2024-01-15' BETWEEN valid_from AND valid_to;
-- Returns the Porto row — correct for January

-- Join orders to the version active at order time (via surrogate key)
SELECT
    o.order_id,
    o.order_date,
    c.city AS city_at_time_of_order
FROM fact_orders   o
JOIN dim_customers c ON o.customer_sk = c.sk;

SCD Type 2 says: "Every version of this record matters — I need to know what it looked like at any point in history." The surrogate key is what makes point-in-time joins work without any date logic at query time.

Part II — Full Refresh vs Incremental

Full Refresh vs Incremental

The fundamental trade-off in data loading

The core idea

🖊️ Analogy — The Whiteboard

Full Refresh is like erasing the entire whiteboard and rewriting everything from your notes — every single time. The board is always perfect and up to date. But if the board has 10 million items and only 100 changed today, you just did 10 million writes to update 100 things.

Incremental is like only writing the new and changed items. Faster, cheaper — but you need to know exactly what changed. And if you accidentally write a duplicate, you can't just erase the board; you have to find and remove it.

DimensionFull RefreshIncremental
What it doesTRUNCATE target, reload all rows from sourceAppend or MERGE only new/changed rows
Row count thresholdIrrelevant — always full costScales with delta size; threshold is a design decision
Failure behaviourRe-run is safe: TRUNCATE wipes partial stateRisky without MERGE logic — can double-load rows
Re-run behaviourNaturally idempotentMust be engineered to be idempotent
Late-arriving dataNo problem — next full reload picks it upCan silently miss rows that fall before the watermark
Idempotent by default?✅ Yes❌ No — requires explicit design
Best forSmall/medium tables, daily snapshotsLarge tables, event streams, hourly loads
dbt equivalentmaterialized='table'materialized='incremental'

Row count threshold — where the cost decision happens

A full refresh costs the same whether 1 row changed or 9 million did. Its cost scales with the total table size. An incremental load's cost scales with the delta size — the number of rows that actually changed.

This means there's a crossover point where incremental starts being worth the added complexity:

📐 Rule of thumb
  • Under 5M rows, less than daily frequency — full refresh. Don't bother with incremental complexity.
  • Over 10M rows, or hourly+ frequency — incremental is worth the investment.
  • 5M–10M rows — profile your actual query cost first. The answer depends on how expensive your compute is and what fraction of rows change per run.

Failure and re-run behaviour

Full Refresh — failure is boring (a compliment)

The full refresh pattern is: TRUNCATE, then INSERT. If it crashes mid-insert, the table is empty or partial until the next run. But the next run TRUNCATEs again (no-op on an empty table) and reloads cleanly. There is no leftover state from the failed run to clean up.

full_refresh.sql
TRUNCATE target_table;
INSERT INTO target_table
SELECT * FROM source_table;
-- If this crashes and reruns → TRUNCATE again (safe), INSERT fresh (correct)

Incremental — failure leaves a footprint

An incremental crash can leave partial data committed. Whether the re-run is safe depends entirely on your write strategy:

Incremental failure scenarios
✗
Naive INSERT, no dedup: 400K of 800K rows committed before crash. Re-run inserts all 800K again. You now have 400K duplicate rows. Reports are inflated.
✓
MERGE / upsert on unique key: Re-run matches existing rows (updates them to same values) and inserts missing ones. Final count = 800K. No duplicates.
✓
Staging table + swap: Write delta to a staging table first, then MERGE into production. A crash in staging leaves production untouched. Re-run re-fills staging and re-merges cleanly.

Late-arriving data

"Late-arriving data" means a record whose event happened in the past but only appeared in the source system now — an offline sale that synced hours later, a sensor reading uploaded in a batch at midnight.

Full Refresh — no problem

The next full reload reads the entire source table, including the late row. It lands in the target on the next cycle. Worst case: one load window of lag.

Incremental — silently missed

If your watermark is 2024-07-15 08:00:00 and a late row has updated_at = 2024-07-14 23:55:00, it falls before the watermark. It will never be picked up. No error. No warning. Just a gap.

The standard mitigations for incremental late arrivals:

late_arrival_mitigation.sql
-- Strategy 1: Lookback buffer — always reprocess the last N hours
-- Catches late arrivals within the buffer window
WHERE updated_at >= {last_watermark} - INTERVAL '3 HOURS'

-- Strategy 2: Partition by event date, not load date
-- Re-run only the affected partitions when late data is detected
WHERE DATE(event_date) = '2024-07-14'  -- reprocess entire partition

-- Strategy 3: Track both timestamps — lets downstream models decide
SELECT
    event_id,
    event_date,                  -- when the event actually happened
    NOW() AS loaded_at            -- when it was loaded into the warehouse
FROM source_events;
Part III — Idempotency
05

Idempotency

The property that lets you retry anything safely

The simplest possible explanation

The word "idempotent" comes from Latin: idem (same) + potens (power). In plain English: doing it twice has the same effect as doing it once.

🛗 Analogy 1 — The Elevator Button

You walk up to an elevator and press the call button. It lights up. You press it again. Nothing changes — it's still lit. Press it 10 more times. Still lit. The state of the world is exactly the same whether you pressed once or a dozen times.

Now compare: a vending machine "insert $1" button. Each press inserts another dollar. 10 presses = $10 inserted. That is not idempotent. Each press changes the world.

📧 Analogy 2 — The Email Send Button

You click "Send" on an important email. Your internet drops. Did it send? You're not sure. You click Send again. If clicking Send is idempotent, you'd get one email delivered regardless. If it's not idempotent (which it usually isn't), your recipient gets two identical emails.

In data pipelines, the "Send" button is your load job. If it's not idempotent and you re-run it after a failure, your recipient (the target table) gets the data twice.

The formal definition

An operation is idempotent if executing it any number of times produces the same final state as executing it exactly once. The guarantee is about the end state, not what happens during execution. In data loading, this means a re-run after any failure never creates duplicate rows, phantom records, or partial state — the pipeline can be safely retried until it succeeds.

Why idempotency is non-negotiable in production

Failures are not exceptional events in data engineering. They are scheduled inconveniences. Network timeouts, database OOM kills, transient connection drops, orchestrator pod restarts — at scale, something fails every day.

If your pipeline is not idempotent, every failure creates a manual incident: a human must check what was partially written, delete the duplicates, reset the watermark, and re-run. At high frequency — hourly or sub-hourly — this becomes unmanageable. You spend more time cleaning up failures than building new features.

Idempotent pipelines enable three things that non-idempotent pipelines can't have:

1
Automated retries

Your orchestrator (Airflow, Prefect, Dagster) can retry failed tasks automatically, with no human involvement and no risk of data corruption. Configure retries=3 and go to sleep.

2
Safe backfills

Re-running a historical date window to fix a bug or reprocess raw data is only safe if the pipeline is idempotent. Otherwise every backfill doubles your data. With idempotency, you can backfill 90 days without fear.

3
Debug with confidence

When a report shows suspicious numbers, you can re-run the pipeline for that date to verify the output — without corrupting the data. A non-idempotent pipeline can't be safely re-run for investigation.

Making a load idempotent — the practical patterns

idempotent_patterns.sql
-- ── Pattern 1: DELETE + INSERT (partition-level idempotency) ──────────
-- Before inserting, delete all rows for the target partition.
-- Re-run: deletes (now-clean) partition, inserts fresh — same result.
DELETE FROM fact_events WHERE event_date = '2024-07-15';
INSERT INTO fact_events
SELECT * FROM stg_events WHERE event_date = '2024-07-15';

-- ── Pattern 2: MERGE / UPSERT on a unique key ─────────────────────────
-- The database itself handles deduplication. Re-run: existing rows are
-- updated to the same values they already hold. Net change: zero.
MERGE INTO fact_events     AS t
USING      stg_events      AS s
ON         t.event_id = s.event_id
WHEN MATCHED     THEN UPDATE SET t.volume = s.volume
WHEN NOT MATCHED THEN INSERT (event_id, event_date, volume)
     VALUES (s.event_id, s.event_date, s.volume);

-- ── Pattern 3: CREATE OR REPLACE (full refresh idempotency) ───────────
-- The entire table is atomically replaced. Re-run: same replacement.
-- No risk of partial state because the swap is atomic.
CREATE OR REPLACE TABLE dim_products AS
SELECT * FROM stg_products;

When Non-Idempotency Bites

A concrete story of what goes wrong — and how to fix it

The setup

You're loading daily meter readings into a fact table. The job runs at 01:00 UTC. It uses a plain INSERT — no deduplication, no MERGE. The assumption is: "this job only runs once per day."

the_naive_load.sql
INSERT INTO fact_meter_readings (meter_id, reading_date, volume_m3, loaded_at)
SELECT  meter_id, reading_date, volume_m3, NOW()
FROM   stg_meter_readings
WHERE  reading_date = '2024-07-15';
-- 820,000 rows to insert
What happens, step by step
1
01:00 UTC: Job starts. Begins inserting 820,000 rows in auto-committed batches of 10,000.
!
01:04 UTC: At row 430,000, the database connection drops. 430,000 rows are permanently committed. The job is marked FAILED.
!
01:09 UTC: Airflow triggers an automatic retry. The WHERE reading_date = '2024-07-15' filter returns all 820,000 rows again — it has no memory of what already exists.
✗
01:14 UTC: Retry succeeds. The target table now has 1,250,000 rows for July 15 — 430,000 duplicates.
✗
08:00 UTC: The daily consumption report runs. Every region shows ~52% more volume for July 15. An anomaly alert pages the on-call engineer.
✗
09:30 UTC: The billing run has already used the inflated data. Some customers are overcharged. The pipeline log shows SUCCESS.
⚠️ The most dangerous part

The orchestrator reports SUCCESS. The pipeline finished cleanly on its second attempt. There is no error, no alert, no red icon. The corruption is invisible until a human compares report numbers to source system totals — which might not happen for days.

The fix — one change, total safety

Replace the plain INSERT with a MERGE on the natural composite key (meter_id + reading_date). Now re-runs are safe: the 430,000 rows already committed get updated to the same values they already hold. Net change: zero duplicates.

the_idempotent_fix.sql
MERGE INTO fact_meter_readings AS target
USING (
    SELECT meter_id, reading_date, volume_m3
    FROM   stg_meter_readings
    WHERE  reading_date = '2024-07-15'
) AS source
ON  target.meter_id    = source.meter_id
AND target.reading_date = source.reading_date

-- Row already exists: update it to the same value (safe no-op on retry)
WHEN MATCHED THEN
    UPDATE SET volume_m3 = source.volume_m3

-- Row doesn't exist yet: insert it fresh
WHEN NOT MATCHED THEN
    INSERT (meter_id, reading_date, volume_m3, loaded_at)
    VALUES (source.meter_id, source.reading_date, source.volume_m3, NOW());
✓ Result

Re-run finds 430,000 rows → updates them to their existing values (no change). Then inserts the remaining 390,000. Final count: exactly 820,000 rows. Report is correct. Billing is correct. On-call engineer sleeps through the night. The orchestrator retried automatically with zero human involvement.

07

Pre-Ship Checklist

Before any incremental load goes to production

  • The load has a unique natural key that a MERGE can use to identify duplicates.
  • Re-running the pipeline for the same date or window produces identical row counts — verified by a test run.
  • There is a lookback buffer sized to the expected late-arrival delay for this source.
  • The watermark is updated after the load commits — never before.
  • A staging table is used for large loads so a mid-run crash doesn't pollute the production target.
  • The orchestrator is configured to auto-retry on transient failure — safe because the load is idempotent.
  • If using SCD Type 2, the fact table stores a surrogate key — not the natural key — as the FK.
  • If using SCD Type 1, confirm that no downstream report needs point-in-time history for the attributes being overwritten.
  • Source deletions are handled — either via soft-delete flags, CDC, or a periodic full-refresh reconciliation.
  • A row count check is in place — alert if the delta is unusually large or zero (indicates a source issue).
