Incremental Models, SCD Type 1, and SCD Type 2

This guide assumes you have never worked with dbt before. The goal is to understand the mental model behind incremental processing and slowly changing dimensions (SCDs).

What Problem Are We Solving?

Imagine a table with 100 million customers. Rebuilding the entire table every time new data arrives would be expensive and slow.

Instead, we want to process only:

  • New records
  • Changed records
  • Deleted records (if needed)

This is the purpose of incremental models.

Part 1: Understanding Incremental Models

An incremental model means:

When the model runs again, don't rebuild everything. Only process what changed since the last run.

Full Refresh

DROP TABLE customers;

CREATE TABLE customers AS
SELECT *
FROM source_customers;

Everything is rebuilt.

Incremental Refresh

INSERT INTO customers
SELECT *
FROM source_customers
WHERE updated_at > last_run_time;

Only new or changed rows are processed.

Key idea: Incremental models save time by touching only changed data.

The Importance of a Unique Key

A unique key identifies exactly one business entity.

Examples:

Table Unique Key
Customers customer_id
Orders order_id
Products product_id

Without a unique key, the system cannot determine:

  • Which row already exists
  • Which row changed
  • Which row should be updated

The unique key is the foundation for everything else in this document.

Incremental Strategy #1: Append

Simplest approach: 

INSERT INTO customers
SELECT *
FROM source_customers;

New rows are added. No updates happen.

Problem: If customer 123 changes their email address, you now have duplicate records.

customer_id email
123 old@email.com
123 new@email.com

Usually not desirable.

Incremental Strategy #2: Delete + Insert

This strategy says:

If a row already exists, delete it first, then insert the newest version.

Example

Existing table:
customer_id name
1 John
New incoming data:
customer_id name
1 John Smith
Process: 
DELETE FROM customers
WHERE customer_id = 1;

INSERT INTO customers
VALUES (1, 'John Smith');
Result:
customer_id name
1 John Smith

Mental Model

"Throw away the old version and replace it with the new one."

Incremental Strategy #3: Merge

Merge is generally smarter and more efficient.

Instead of deleting and inserting, it decides:

  • If the row exists → UPDATE it
  • If the row doesn't exist → INSERT it

Pseudo Logic

IF customer exists
    UPDATE customer
ELSE
    INSERT customer

SQL Example

MERGE INTO customers target
USING incoming_customers source

ON target.customer_id = source.customer_id

WHEN MATCHED THEN
    UPDATE SET
        name = source.name

WHEN NOT MATCHED THEN
    INSERT (customer_id, name)
    VALUES (source.customer_id, source.name);
Most modern data warehouses prefer MERGE because it is efficient and easier to maintain.

How Incremental Strategies Relate to SCDs

Now we move to dimensional modeling.

The question becomes:

What should happen when an attribute changes?
Example:
customer_id city
1 Lisbon
Tomorrow:
customer_id city
1 Porto
Do we:
  • Overwrite Lisbon?
  • Keep Lisbon and Porto?
Those are SCD decisions.

SCD Type 1

Definition

SCD Type 1 overwrites old values. History is not preserved.

Example

Before:
customer_id city
1 Lisbon
After change:
customer_id city
1 Porto

The Lisbon value is gone forever.

Typical Implementation

PostgreSQL: 
INSERT INTO dim_customer (
    customer_id,
    customer_name,
    city
)
VALUES (
    1,
    'John',
    'Porto'
)

ON CONFLICT (customer_id)

DO UPDATE SET
    customer_name = EXCLUDED.customer_name,
    city = EXCLUDED.city;

Mental Model

Always keep the latest truth. Forget the past.

SCD Type 2

Definition

SCD Type 2 preserves history. Every change creates a new version.

Goal

We want answers like:

  • Where did the customer live today?
  • Where did they live last year?
  • What was true on a specific date?

Columns Used in SCD Type 2

Column Purpose
valid_from Version start date
valid_to Version end date
is_current Current active version

Example Data

Initial State

customer_id city valid_from valid_to is_current
1 Lisbon 2025-01-01 NULL true

Customer Moves to Porto

Instead of updating the row:

Step 1: Close Current Version

UPDATE dim_customer
SET
    valid_to = CURRENT_DATE,
    is_current = false
WHERE customer_id = 1
AND is_current = true;

Step 2: Create New Version

INSERT INTO dim_customer (
    customer_id,
    city,
    valid_from,
    valid_to,
    is_current
)
VALUES (
    1,
    'Porto',
    CURRENT_DATE,
    NULL,
    true
);

Result

customer_id city valid_from valid_to is_current
1 Lisbon 2025-01-01 2025-08-01 false
1 Porto 2025-08-01 NULL true

What Happened?

Nothing was overwritten.

We preserved the old version and added a new one.

SCD Type 1 vs Type 2

Feature SCD Type 1 SCD Type 2
Stores history No Yes
Updates existing row Yes No
Creates new version No Yes
Current state available Yes Yes
Past state available No Yes

The Big Picture

Remember These 4 Ideas

  1. Incremental Models
    Process only changed data instead of rebuilding everything.
  2. Unique Key
    Identifies exactly one business entity.
  3. Delete+Insert and Merge
    Ways to keep incremental tables synchronized with source data.
  4. SCD Type 1 vs Type 2
    Type 1 overwrites history.
    Type 2 preserves history using valid_from, valid_to, and is_current.

One-Sentence Summary

Incremental models determine how data is loaded efficiently, while SCD Type 1 and Type 2 determine how changes to existing records are stored over time.
